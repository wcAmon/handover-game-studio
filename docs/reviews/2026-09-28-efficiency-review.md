## 發現與建議

### 1. 最高優先：依變更範圍選擇驗證，沿用可驗證的既有結果
#36～44 的 runtime src/public 相同；八份可直接讀到耗時的報告，每班相同專項 e2e 4.6m＋snap 1.7m，合計至少 50.4 分鐘，尚不含 #41、建置、讀圖和歸檔。這些驗證能證明原遊戲仍可用，不能證明新素材接入有效。

證據：遊戲 docs/T-047-validation.md:21、T-053-validation.md:23、T-055-validation.md:25、T-056-validation.md:14、T-057-validation.md:18、T-059-validation.md:13、T-060-validation.md:11、T-061-validation.md:11。Git trees 見 metrics。

建議新增 validation receipt：記錄實際測試輸入指紋（src/public、測試／config、lockfile、工具與瀏覽器版本、必要環境），而不只比 commit。相同輸入與環境可引用既有通過證據；來源／文件班只跑新來源的 alpha、註冊、縮圖和組裝檢查；runtime 接入跑影響範圍，里程碑跑全套。fingerprint 不符或先前失敗必須重跑。

這不是刪除測試；但現有任務明訂逐班跑，需先更新驗證政策再執行，不能讓 agent 自行跳過。50.4 分鐘是重複項目耗時的可改善範圍，非保證全部節省。

### 2. 以可玩交付為任務邊界，限制拆班的深度
來源、分件、來源組裝、透明加工、實機整合、統合驗收一路拆開；貨車從 #36 到 #44 還未接入。docs/T-022-plan.md:30、48、54～80 明確記錄此拆分。

建議仍維持一班一個 NOW，但 NOW 改為可驗收產品成果，例如「貨車能以正式素材行駛並補給」。來源與加工可跨班維持同一交付 ID，子步驟放 checklist；正常換全新 context，不把每個圖板當新里程碑。連續 2～3 班尚無可執行候選時，觸發範圍與路徑重估；不要武斷把合理素材探索判成失敗。

### 3. 把生成與確定性加工分開，統一素材工具
#18 多次要求生成器去背，仍收到 RGB／重畫，T-027-validation.md:19～29 有逐件證據。後續確定性加工已解決多數問題，應把成熟處理器變成統一路徑，而非重複探索。現 game/scripts/art 有 64 個直接子項（含程式，非全部獨立工具）。

建議：生圖負責外觀；經授權的確定性加工負責 alpha、裁切、尺寸、錨點；每素材上限兩次同類生成失敗後換方法。共用 manifest/schema、processor、review renderer；保留類型特有檢查。統一品質標準，避免每個零件再造一套工具。透明加工方式須遵守目前生圖工具和專案授權。

### 4. 以最終顯示尺寸決定美術公差
T-059-validation.md:16 與 docs/T-022-plan.md:62 記錄大量像素接合／中間尺寸精度，確實防止漂浮、斷接，但部分精度遠超小尺寸畫面辨識需求。

建議分成硬閘門（碰撞／腳底／可辨識輪數／無破洞／不露背景）與視覺改善項（亞像素邊緣、不可見色差）。門檻依最終 1×畫面、動態與參考圖定，不以數值越小越好。任何調整先記錄理由，不取消人類核准的美術要求，也不把佔位標成正式。

### 5. 新 context 保留，但縮短必讀交班
目前交班接近 8,000 字上限，常携帶已穩定的整套玩法座標與歷代素材數值。shift/SKILL.md:17 要完整讀，:22 要重驗 STATE，:23 又鼓勵切小；harness/continuous.py:59～61 重複要求同樣入口。這是可見固定開銷，未量到它單獨占用多少分鐘。

建議交班目標 1,500～2,500 字，固定五項：NOW、上一班結果與證據指紋、這班必讀檔、風險、下一步。穩定契約放模組文件，只有相關任務才讀；北極星與 approval 仍須有效。保持全新 context，不靠 resume 延長對話。

### 6. 監督器要看交付進展，也要有正式的收班後暫停
目前 progress 只比交班 hash 與 HEAD（harness/continuous.py:32～36、138～150）。新增文件或把任務拆細就能被判有進展，沒有里程碑停滯偵測。停止目前只有立即 stop；此次收班後停用臨時 helper 協調，status 也無清楚的 draining 狀態。

建議新增 drain/pause-after-shift，當班結束正常驗證提交後轉 paused，不啟下一班；status 顯示當前 agent 心跳、已運行時間、pending pause。進度另記里程碑完成條件、玩家可見交付、artifact readiness、連續未接入班數與測試耗時。停滯時先產生策略調整，不自動無限新增任務。

## 建議落地順序
1. 原生收班後暫停與準確狀態；保留現有暫停要求。
2. 驗證指紋／分層驗證，先消除已證實的重複成本。
3. 縮短交班、改用交付 ID＋子步驟，增加停滯重估。
4. 整併素材加工與驗收工具，在現有素材上回歸。
5. 以上穩定後再考慮素材和玩法的隔離並行；目前同目錄／共用 test-results 有衝突歷史，不建議直接加 agent 數量。
